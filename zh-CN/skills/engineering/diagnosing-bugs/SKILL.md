# Diagnosing Bugs

针对疑难 bug 的一套纪律。只有在明确有理由时才跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你所接触区域的 ADR。

## 脱敏

本技能会让你展示命令、输出和捕获到的产物。**先脱敏每一个机密**——在其位置写 `<REDACTED>`。针对环境变量构建循环，让凭据留在环境中，而不是出现在你展示的内容里。捕获到的产物会携带认证头：只引用携带信号的那些行。

如果脱敏后的输出不足以诊断 bug，就明说并询问用户。

## 阶段 1——建立反馈回路

**这就是本技能的核心。** 其他一切都是机械步骤。如果你为这个 bug 拥有一个 **tight（紧凑）**的通过/失败信号——一个会因*这个* bug 变红（goes red）的信号——你就能找到原因；二分、假设检验和插桩都只是在消费它。如果你没有，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建方法——大致按以下顺序尝试

1. **失败测试**，放在任何能触达 bug 的 seam 处——单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向正在运行的开发服务器。
3. **CLI 调用**，使用夹具输入，把 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，在 DOM/console/network 上断言。
5. **重放捕获的 trace。** 把真实的网络请求 / 载荷 / 事件日志保存到磁盘；在隔离环境中通过代码路径重放它。
6. **一次性 harness。** 启动系统的一个最小子集（一个服务、mock 依赖），用单次函数调用走 bug 代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是“有时输出错误”，运行 1000 个随机输入，寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”，以便 `git bisect run` 可以运行。
9. **差分循环。** 把同一输入跑在旧版本 vs 新版本（或两种配置）上，diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人类点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让循环仍保持结构化。捕获到的输出回流给你。

建立正确的反馈回路，bug 就修好了 90%。

### 收紧循环

把循环当作产品对待。一旦你有了*一个*循环，就**收紧**它：

- 能更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是“没崩溃”。）
- 能更确定吗？（固定时间、给 RNG 设种子、隔离文件系统、冻结网络。）

一个 30 秒的偶发循环几乎不比没有循环强；一个 2 秒的确定性循环才算紧凑——这是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发器循环 100 次、并行化、增加压力、收窄时间窗口、注入 sleep。复现率 50% 的偶发 bug 可以调试；1% 的不能——不断提高复现率，直到可以调试。

### 当你确实无法建立循环时

停下来明确说明。列出你尝试过的方法。向用户索要：(a) 能复现它的环境访问权限；(b) 脱敏的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏）；或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下进入假设。

### 完成标准——一个会变红的紧凑循环

当循环**紧凑**且**能变红（red-capable）**时，阶段 1 完成：你能说出一条**命令**——脚本路径、测试调用或 curl——并且你**至少已经运行过一次**（展示调用和输出，脱敏），它还必须满足：

- [ ] **能变红**——它驱动真实的 bug 代码路径，并断言**用户描述的确切症状**，因此能在这个 bug 上变红，修复后变绿。不是“运行不出错”——它必须能*抓住这个具体的 bug*。
- [ ] **确定性**——每次运行结论相同（偶发 bug：按上文固定一个高复现率）。
- [ ] **快**——以秒计，不是分钟。
- [ ] **agent 可运行**——你能无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 才允许人在环中。

如果你发现自己在命令尚不存在时就阅读代码构建理论，**停下——直接跳进假设正是本技能要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2——复现 + 最小化

运行循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是碰巧在附近的另一种失败。错误的 bug = 错误的修复。
- [ ] 失败可以跨多次运行复现（非确定性 bug 则是复现率足够高，可以对着它调试）。
- [ ] 你已捕获确切症状（错误消息、错误输出、缓慢耗时），让后续阶段能验证修复确实解决了它。

### 最小化

一旦变红，就把复现缩小到**仍然会变红的最小场景**。**一次一个**地削减输入、调用方、配置、数据和步骤，每次削减后重跑循环——只保留对失败有承重作用的东西。

为什么值得：最小复现会缩小阶段 3 的假设空间（剩下可怀疑的变动部件更少），并成为阶段 5 干净的回归测试。

当**每个剩余元素都有承重作用**——移除其中任何一个都会让循环变绿——就完成了。

在完成复现**和**最小化之前，不要继续。

## 阶段 3——提出假设

在测试任何假设之前，先提出**3–5 个排好序的假设**。只提出一个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：陈述它所做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。”

如果你说不出预测，这个假设就只是一种感觉——丢弃或打磨它。

**测试前把排序列表展示给用户。** 他们往往拥有能瞬间重排的领域知识（“我们刚对 #3 部署了一个变更”），或者知道哪些假设已经被排除。便宜的检查点，却能省下大量时间。不要因此阻塞——如果用户不在键盘前，就按你的排序继续。

## 阶段 4——插桩

每个探针必须对应阶段 3 中的一条具体预测。**一次只改变一个变量。**

工具优先级：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十行日志。
2. **定向日志**，放在能区分各假设的边界处。
3. 绝不“把一切都打日志然后 grep”。

**给每条调试日志打上唯一前缀**，例如 `[DEBUG-a4f2]`。收尾清理就变成一次 grep。无标签日志会留下；带标签日志会被清掉。

**性能分支。** 对于性能回退，日志通常不对。改为：建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5——修复 + 回归测试

在**修复之前**写回归测试——但只有当存在一个**正确的 seam** 时才写。

正确的 seam 是指测试能在调用点处、按照其真实发生方式走**真实 bug 模式**的 seam。如果唯一可用的 seam 太浅（bug 需要多个调用方，却只有单调用方测试；单元测试无法复现触发 bug 的调用链），在那里写回归测试只会带来虚假信心。

**如果没有正确的 seam，这本身就是发现。** 记下来。代码库架构正在阻止这个 bug 被锁死。把这一点标记出来，留给下一阶段。

如果存在正确的 seam：

1. 把最小复现变成该 seam 处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 对原始（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6——清理

宣布完成前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或 seam 缺失已记录在案）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到清晰标记的调试位置）
- [ ] 被证明正确的假设写进 commit / PR 消息——让下一位调试者能学到东西
