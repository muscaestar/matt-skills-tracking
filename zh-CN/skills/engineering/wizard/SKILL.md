# Wizard

**向导（wizard）**是一个 bash 脚本，一步一步地引导人类完成一个手工流程——这种流程手工做很繁琐，每次向 AI 重新解释也很繁琐。它打开每个 URL，精确说明要点哪里、复制什么，捕获这些值，把它们写到该去的地方（`.env`、GitHub secrets），在每个阶段进行确认，并显示还剩多少个阶段。它可能配置第三方服务、执行一次性迁移，或把项目从一种状态迁移到另一种状态。

令人愉悦的 UX 已经由 [template.sh](template.sh) 解决了——逐阶段进度、确认闸门、跨平台 URL 打开（包括 WSL）、隐藏式 secret 输入、幂等的 `.env` 更新、`gh secret`/`gh variable` 写入，以及结尾总结。**你的工作只是界定流程范围并编写它的各个阶段。** `STAGES` 标记以上的库在每个向导中都完全相同；这种一致性正是意义所在——永远不要手工编辑它。

向导默认是临时的——为一次运行而建，保存到 scratch 或 `scripts/` 路径，任务完成后删除。只有当用户想要一个应该留在仓库里的可重复设置路径时才提交它。

## 流程

### 1. 界定流程范围

理出人类必须执行的每一个手工步骤，以及沿途捕获的每一个值。先读仓库——不要空着手问：

- 对于设置类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是向导必须产出的一个值）。
- 对于迁移或切换类：当前状态、目标状态，以及两者之间不可逆的操作。

然后向用户展示按序排列的阶段列表和每个阶段产出的值，并确认——他们可能会增删或调整顺序。

**完成标准：** 每个阶段都按序命名，并且对于每个被捕获的值，你知道 (a) 人类从哪里得到它，(b) 它写到哪里（`.env`、GitHub secret、两者，或都不写——有些阶段是纯操作），以及 (c) 它是 secret（隐藏输入）还是公开值。

### 2. 绘制每个阶段的路径

为每个阶段写出人类要走的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、它填入哪个变量——例如 "Dashboard → Developers → API keys → Reveal test key → copy"。在你并不真正了解当前 UI 或确切命令的地方，明说并询问用户或查阅文档——永远不要编造可能不存在的步骤。

**完成标准：** 每个阶段都能追溯到陌生人也能照着做的具体指示。

### 3. 编写向导

把 `template.sh` 复制到目标路径。用每一步一个 `stage` 替换示例阶段，按依赖顺序排列。使用库提供的辅助函数——`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`——并把 `TOTAL_STAGES` 设为你写出的阶段数。

坚守模板设定的标准：先打开 URL 再索要它的值；任何 secret 都用 `ask_secret`；每个要持久化的值都 `write_env`；只有 CI 真正需要的值才 `set_secret`；任何不可逆操作之前都 `confirm`。每个 `stage` 会清屏，让只有当前步骤可见——让一个阶段只聚焦一个任务，这样人类需要的任何内容都不会滚出屏幕。不要动标记以上的库。

### 4. 验证并交接

- `bash -n <script>`；如果有 `shellcheck` 就运行它。
- `chmod +x <script>`。
- 不要自己端到端运行它——它会打开浏览器并阻塞等待人类输入。改为静态追踪：第 1 步中的每个值都被捕获并落到了第 1 步指定的位置，且每个 `set_secret` 的名字与 CI 中的 `secrets.*` 引用精确匹配。
- 告诉用户如何运行它。如果它是一个可重复的设置路径，提交它并从 README 链接过去，让下一个人运行脚本而不是去问 AI。
