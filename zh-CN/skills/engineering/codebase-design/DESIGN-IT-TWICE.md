# 设计两次

当用户想为选定的深化候选探索替代接口时，使用这个并行子 agent 模式。源自 Ousterhout 的 “Design It Twice”——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 框定问题空间

在启动子 agent 之前，先为选定的候选写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖什么，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示意性代码草图，让约束变得具体——不是提案，只是把约束具体化的方式

把它展示给用户，然后立即进入第 2 步。子 agent 并行工作时，用户一边阅读一边思考。

### 2. 启动子 agent

并行启动 3 个以上子 agent。每个都必须为深化后的模块产出一个**截然不同**的接口。

给每个子 agent 一份独立的技术简报（文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 中的依赖类别、接缝后面是什么）。这份简报独立于第 1 步面向用户的问题空间说明。给每个 agent 不同的设计约束：

- Agent 1：“最小化接口——目标是最多 1–3 个入口。最大化每个入口的杠杆。”
- Agent 2：“最大化灵活性——支持许多用例和扩展。”
- Agent 3：“为最常见的调用方优化——让默认情形变得轻而易举。”
- Agent 4（如果适用）：“围绕端口与适配器（ports & adapters）设计跨接缝依赖。”

把 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇都放进简报，让每个子 agent 的命名既符合架构语言，也符合项目领域语言。

每个子 agent 输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 展示调用方如何使用的使用示例
3. 实现隐藏在接缝后面的内容
4. 依赖策略和 adapter（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里杠杆高，哪里薄

### 3. 展示并比较

逐个展示设计，让用户能消化每一个，然后用文字比较它们。从**深度**（接口处的杠杆）、**局部性**（变更集中的位置）和**接缝位置**三个维度对比。

比较之后，给出你自己的推荐：你认为哪个设计最强以及为什么。如果不同设计的元素能很好结合，提出一个混合方案。要有明确观点——用户要的是有力判断，不是菜单。
