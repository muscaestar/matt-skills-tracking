对 `HEAD` 与用户提供的固定点之间的 diff 做双轴审查：

- **Standards**——代码是否符合本仓库成文的编码标准？
- **Spec**——代码是否忠实实现了来源 issue / 规格？

两个轴都以**并行子 agent**运行，以免互相污染上下文；随后本技能汇总它们的发现。

你应该已经拿到 issue 跟踪器信息。如果 `docs/agents/issue-tracker.md` 缺失，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户说的任何内容就是固定点——commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果他们没有指定，就去问。

把 diff 命令一次性记下来：`git diff <fixed-point>...HEAD`（三点形式，这样是与 merge-base 比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`），且 diff 非空。错误的 ref 或空 diff 应当在这里就失败——而不是在两个并行子 agent 内部。

### 2. 找到规格来源

按以下顺序寻找来源规格：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——按 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果什么都没找到，问用户规格在哪里。如果他们说没有，**Spec** 子 agent 将跳过，并报告 “no spec available”。

### 3. 找到标准来源

仓库中任何说明代码应如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

无论仓库记录了什么，Standards 轴始终包含下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（《Refactoring》第 3 章），即使仓库没有任何文档也适用。有两条规则约束它：

- **仓库优先。** 成文的仓库标准永远胜出；如果它认可某处基线会标记的写法，就抑制该坏味道。
- **始终是判断。** 每个坏味道都是带标签的启发式（“可能是 Feature Envy”），绝不是硬性违规——而且，和这里的任何标准一样，工具已经在强制执行的任何内容都跳过。

每个坏味道按*是什么* → *如何修*来阅读；把它们与 diff 对照：

- **Mysterious Name**——函数、变量或类型的名字没有揭示它的作用或内容。→ 重命名；如果想不到一个诚实的名字，说明设计本身模糊不清。
- **Duplicated Code**——同一逻辑形状在改动的多个 hunk 或文件中出现。→ 提取共享形状，让两处都调用它。
- **Feature Envy**——某个方法访问另一对象数据的次数超过访问自己的。→ 把方法移到它所羡慕的数据上。
- **Data Clumps**——同一组字段或参数总是一起出现（一个想诞生的类型）。→ 把它们捆绑成一个类型，传递这个类型。
- **Primitive Obsession**——用原始类型或字符串顶替一个值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **Repeated Switches**——同一类型上相同的 `switch`/`if` 级联在改动中反复出现。→ 用多态替代，或让各处共享同一张映射。
- **Shotgun Surgery**——一个逻辑改动迫使在 diff 中许多文件散落修改。→ 把一起变化的东西收拢到一个模块。
- **Divergent Change**——一个文件或模块因多个互不相关的原因被修改。→ 拆分，让每个模块只为一个原因变化。
- **Speculative Generality**——为规格不需要的需求添加抽象、参数或钩子。→ 删掉；不断内联回去，直到真实需求出现。
- **Message Chains**——调用方不应依赖的 `a.b().c().d()` 长链导航。→ 把这段行走隐藏到第一个对象上的一个方法后面。
- **Middle Man**——一个类或函数大部分只是在转发。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest**——子类或实现者忽略或覆盖了所继承的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子 agent

**Standards 子 agent 提示词**——包含：

- 完整的 diff 命令和提交列表。
- 你在第 3 步找到的标准来源文件列表，**外加第 3 步的坏味道基线全文粘贴**——子 agent 没有其他途径获得它。
- 任务说明：“报告——在相关的每个文件/hunk 上——(a) diff 违反成文标准的每一处：引用该标准（文件 + 规则）；(b) 你发现的任何基线坏味道：报出名字并引用 hunk。区分硬违规和判断——违反成文标准可能是硬违规，但基线坏味道始终是判断，而且成文的仓库标准优先于基线。跳过任何工具已在强制执行的内容。400 词以内。”

**Spec 子 agent 提示词**——包含：

- diff 命令和提交列表。
- 规格的路径或获取到的内容。
- 任务说明：“报告：(a) 规格要求但缺失或只完成了一部分的需求；(b) diff 中规格没有要求的行为（范围蔓延）；(c) 看起来已实现、但实现方式可疑的需求。每项发现都要引用规格原文。400 词以内。”

如果规格缺失，跳过 Spec 子 agent，并在最终报告中注明。

### 5. 汇总

把两份报告分别放在 `## Standards` 和 `## Spec` 标题下，逐字呈现或稍作整理。**不要**合并或重新排序发现——两个轴刻意保持分离（见“为什么需要两个轴”）。

最后用一句话总结：每个轴的发现总数，以及*每个轴内*最严重的问题（如果有）。不要跨轴选出一个总冠军——那正是这种分离要防止的重新排序。

## 为什么需要两个轴

一个改动可能通过一个轴而通不过另一个轴：

- 代码遵循了所有标准，却实现了错误的东西 → **Standards 通过，Spec 不通过。**
- 代码完全做到了 issue 要求的事，却破坏了项目约定 → **Spec 通过，Standards 不通过。**

分开报告可以防止一个轴掩盖另一个轴。
