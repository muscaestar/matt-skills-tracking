# Triage

让项目 issue 跟踪器上的 issue 在一个由 triage 角色构成的小型状态机中流转。

如果本仓库把外部 pull request 视为请求来源（见 issue-tracker 配置），triage 也覆盖它们：**PR 就是附带代码的 issue**——同样的角色、同样的状态、同样的状态机，只有少量差异在下文中标注"for a PR"。单独的 `#42` 按跟踪器配置解析为 issue 或 PR。

triage 期间发布到 issue 跟踪器的每条评论或 issue **必须**以下面这个免责声明开头：

> 该免责声明保留英文——它是发布到 issue 跟踪器上的实际文本。

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)——如何撰写耐久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)——`.out-of-scope/` 知识库如何工作

## 角色

两个**类别**角色：

- `bug`——有东西坏了
- `enhancement`——新功能或改进

五个**状态**角色：

- `needs-triage`——维护者需要评估
- `needs-info`——等待报告者提供更多信息
- `ready-for-agent`——规格完整，可以交给 AFK agent
- `ready-for-human`——需要人工实现
- `wontfix`——不会被处理

对于 PR，同样的状态对照附带的代码来读：`ready-for-agent` 意味着简报已附、agent 应该对 diff 做下一步；`ready-for-human` 意味着已准备好由人工合并。

每个被 triage 的 issue 应当恰好携带一个类别角色和一个状态角色。如果状态角色冲突，先标记出来并询问维护者，再做任何其他事。

这些是规范角色名——issue 跟踪器中实际使用的标签字符串可能不同。映射关系应该已经提供给你了。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态流转：无标签的 issue 通常先进入 `needs-triage`；从那里流向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖——对看起来不寻常的流转先标记并询问，再继续。

## 调用方式

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并行动。例如：

- "Show me anything that needs my attention"（给我看所有需要我关注的东西）
- "Let's look at #42"（issue 或 PR）（我们看看 #42）
- "Move #42 to ready-for-agent"（把 #42 移动到 ready-for-agent）
- "What's ready for agents to pick up?"（哪些已经准备好可以交给 agent 了？）

## 展示需要关注的内容

查询 issue 跟踪器，按最旧优先呈现三个桶：

1. **Unlabeled**——从未 triage 过。
2. **`needs-triage`**——评估进行中。
3. **自上次 triage 笔记以来有报告者活动的 `needs-info`**——需要重新评估。

当 PR 在范围内时，把外部 PR 纳入这些桶，并给每行打上 `[PR]` 或 `[issue]` 标记。发现阶段只浮现*外部* PR（跟踪器配置定义了谁算外部）——协作者进行中的 PR 不是 triage 工作。这个过滤仅用于发现；被显式点名的 PR 无论作者是谁都会被 triage。

显示数量和每项的一行摘要。让维护者挑选。

## Triage 一个具体的 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析任何已有的 triage 笔记，以免重复询问已解决的问题。使用项目领域术语表探索代码库，尊重该区域内的 ADR。对照代码库做两项检查：(a) **冗余**——按领域概念（而不只是请求的措辞）搜索所请求行为的现有实现，并报告你查找过的位置。如果找到了，这就是一个"已实现"的 `wontfix`（第 5 步）。(b) **曾被拒绝**——阅读 `.out-of-scope/*.md`，浮现任何与该请求相似的文件。

2. **给出建议。** 告诉维护者你的类别和状态建议及理由，外加与请求相关的简短代码库摘要——包括它是否已经被实现。等待指示。

3. **验证论断。** 在任何 grilling 之前，检查论断是否成立。对于 bug，按报告者的步骤复现它。对于 PR，确认 diff 做到了它声称的事——checkout 出来，运行相关测试或命令。报告结果：已确认（附代码路径）、复现失败，或细节不足（一个强烈的 `needs-info` 信号）。一次确认的验证能让 agent 简报有力得多。

4. **Grill（如需要）。** 如果请求需要充实，调用 Skill 工具两次，分别调用 "grilling" 和 "domain-modeling"——以一轮一轮问题的方式把它 grill 成形，随着决策落地，同步打磨领域术语并就地更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`——发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`——结构与 agent 简报相同，但注明为什么不能委托（需要判断、外部访问、设计决策、手工测试）。
   - `needs-info`——发布 triage 笔记（模板见下）。
   - `wontfix`——关闭，评论内容取决于*原因*：
     - **已实现**——改动已经存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求的，不是给已建成的功能的）。
     - **被拒绝（bug）**——礼貌地解释，然后关闭。
     - **被拒绝（enhancement）**——写入 `.out-of-scope/`，在评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`——应用该角色。如果有部分进展，可选地发一条评论。

## 快速状态覆盖

如果维护者说 "move #42 to ready-for-agent"（把 #42 移动到 ready-for-agent），信任他们并直接应用该角色。确认你即将做的事（角色变更、评论、关闭），然后行动。跳过 grilling。如果在没有 grilling 会话的情况下移动到 `ready-for-agent`，问他们是否想写一份 agent 简报。

## Needs-info 模板

> 模板字段名保留英文——这是发布到 issue 上的实际评论格式；含义见中文注释。

```markdown
## Triage Notes

**What we've established so far:**    # 我们目前已确认的内容

- point 1    # 要点 1
- point 2

**What we still need from you (@reporter):**    # 我们仍然需要你（@报告者）提供的

- question 1    # 问题 1
- question 2
```

把 grilling 期间解决的所有内容记录在 "established so far"（已确认的内容）下，以免工作丢失。问题必须具体、可执行，而不是 "please provide more info"（请提供更多信息）。

## 恢复之前的会话

如果 issue 或 PR 上已有 triage 笔记，阅读它们，检查报告者是否回答了悬而未决的问题，并在继续之前呈现更新后的图景。不要重复询问已解决的问题。
