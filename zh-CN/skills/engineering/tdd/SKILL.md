# 测试驱动开发（Test-Driven Development）

TDD 就是 red → green 循环。本技能是让这个循环产出值得保留的测试的参考：什么是好测试、测试写在哪里、反模式，以及循环的规则。每个小节在每个循环周期都适用——在循环之前和之中查阅它们，而不是之后。

探索代码库时，阅读 `CONTEXT.md`（如果存在），让测试名和接口词汇与项目的领域语言保持一致，并尊重你触及区域内的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是验证实现细节。代码可以完全改变；测试不应该变。好测试读起来像规格说明——"user can checkout with valid cart" 精确告诉你存在什么能力——并且能经受重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## Seam——测试写在哪里

**Seam** 是你在其上做测试的公开边界：你在那里观察行为而不伸手进内部。测试位于 seam 上，绝不针对内部实现。

**只在预先约定的 seam 上测试。** 在写任何测试之前，写下被测的 seam 并与用户确认。没有测试写在未经确认的 seam 上。你不可能测试所有东西——预先约定 seam，是让测试投入落在关键路径和复杂逻辑上、而不是每个边角案例上的方法。

问："公开接口是什么？我们应该测试哪些 seam？"

当接口本身的形态也存疑时——模块应该多深、seam 应该落在哪、接口应该暴露什么——用 "codebase-design" 调用 Skill 工具获取词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同来源，它是一份供查阅的参考，不是一个要运行的会话。

## 反模式

- **与实现耦合（Implementation-coupled）**——mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。征兆：你重构但行为没变时，测试却坏了。
- **同义反复（Tautological）**——断言用与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导的 snapshot、一个常量断言等于它自己），因此它天然通过，永远不可能与代码产生分歧。期望值必须来自独立的真相来源——一个已知正确的字面量、一个手工算过的例子、规格说明。
- **水平切片（Horizontal slicing）**——先写所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测的是东西的_形状_而不是面向用户的行为，测试对真实变化失去敏感性，而且你在理解实现之前就锁定了测试结构。改为按**垂直切片**工作——一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，对上一个周期教给你的东西做出响应。

## 循环的规则

- **先 red 后 green。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，不要添加投机性的功能。
- **一次一个切片。** 每个周期一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `code-review` 技能），不属于 red → green 实现周期。
