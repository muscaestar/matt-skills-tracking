# ADR 格式

ADR 存放在 `docs/adr/` 中，使用连续编号：`0001-slug.md`、`0002-slug.md`，依此类推。

按需创建 `docs/adr/` 目录——只在需要第一个 ADR 时创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以只有一个段落。价值在于记录*一个决策已经做出*和*为什么*——而不在于填满栏目。

## 可选栏目

只有当这些栏目确实能增加价值时才加入。大多数 ADR 不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策被重新审视时有用
- **Considered Options**——只有当被否定的替代方案值得记住时才写
- **Consequences**——只有当不明显的下游影响需要被指出时才写

## 编号

扫描 `docs/adr/` 中现有的最大编号，然后加一。

## 何时提议 ADR

以下三点必须全部成立：

1. **难以逆转**——日后改变主意的代价是切实的
2. **没有上下文会很意外**——未来的读者会看着代码疑惑“他们到底为什么这么做？”
3. **真实权衡的结果**——确实存在其他选项，而你出于具体理由选了这一个

如果决策容易逆转，跳过它——你将来直接逆转就好。如果它不令人意外，没人会疑惑为什么。如果不存在真正的替代方案，那除了“我们做了显而易见的事”，没什么可记录的。

### 哪些情况符合条件

- **架构形状。** “我们使用 monorepo。”“写模型是事件溯源的，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带有锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库——只是那些换掉要花一个季度的。
- **边界和范围决策。** “Customer 数据由 Customer 上下文拥有；其他上下文只通过 ID 引用它。”明确的“不做什么”和“做什么”一样有价值。
- **对显而易见路径的刻意偏离。** “我们使用手写 SQL 而不是 ORM，因为 X。”任何合理读者都会假定相反做法的内容。这些记录能阻止下一位工程师“修好”一个刻意为之的东西。
- **代码中不可见的约束。** “因为合规要求，我们不能用 AWS。”“由于合作伙伴 API 合约，响应时间必须低于 200ms。”
- **被否定的替代方案，且否定原因不明显。** 如果你考虑过 GraphQL 却因微妙原因选择了 REST，就记录下来——否则六个月后又会有人提议 GraphQL。
