# Prototype

原型是**用来回答一个问题的一次性代码**。问题决定它的形态。

## 选择分支

确定正在回答的是哪个问题——从用户提示、周边代码中判断，或用户在场时直接询问：

- **“这个逻辑 / 状态模型是否顺手？”** → [LOGIC.md](LOGIC.md)。构建一个可共享的 HTML 文件——自由把玩的按钮 + 分页的引导式走查——把状态机推过那些纸面上难以推理的用例，而且非开发者也能操作。
- **“这应该长什么样？”** → [UI.md](UI.md)。在单一路由上生成几个截然不同的 UI 变体，通过 URL 搜索参数和悬浮底栏切换。

两条分支产出截然不同的产物——选错会浪费整个原型。如果问题确实含糊且联系不上用户，默认选与周边代码更匹配的分支（后端模块 → logic；页面或组件 → UI），并在原型顶部声明这一假设。

## 两条分支都适用的规则

1. **从第一天起就是一次性的，并清楚标记。** 把原型代码放在它真正会被使用的位置附近（要为之做原型的模块或页面旁边），让上下文一目了然——但命名要让随便一个读者都看得出它是原型，而不是生产代码。对于一次性 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **运行起来要极其简单。** UI 原型从项目任务运行器的一条命令开始——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击即开的单个 HTML 文件。无论哪种，启动时都不需要思考。
3. **默认无持久化。** 状态只存在于内存。持久化是原型要*检验*的东西，而不是它应当依赖的东西。如果问题明确涉及数据库，使用 scratch 数据库或本地文件，并起一个清晰的 “PROTOTYPE — wipe me” 名字。
4. **跳过打磨。** 不写测试，不做超出“让原型*可运行*”的错误处理，不做抽象。目标是快速学到东西。
5. **暴露状态。** 每次动作后（logic）或每次切换变体时（UI），打印或渲染完整相关状态，让用户看到什么变了。
6. **完成后捕获。** 把经过验证的决策折入真实代码，然后把原型本身捕获为**一手来源**：提交到 main 之外的一次性分支，并在实现 issue 上留下指向该分支的上下文指针。答案也要捕获——结论和它解决的问题——写进 issue 或提交。main 分支只保留经过验证的决策。
