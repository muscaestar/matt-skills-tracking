# UI 原型

在单一路由上生成**几个截然不同的 UI 变体**，用悬浮底栏切换。用户在浏览器中来回切换变体，选一个（或从每个里面各偷一点），然后把其余扔掉。

如果问题关于逻辑/状态而不是外观——分支错了。用 [LOGIC.md](LOGIC.md)。

## 何时该用这种形态

- “这个页面应该长什么样？”
- “在确定之前，我想看看这个仪表盘的几个选项。”
- “试试设置页的另一种布局。”
- 任何用户原本会在脑子里三个模糊线框图之间纠结一天的情形。

## 两种子形态——强烈偏好子形态 A

当 UI 原型**贴着应用其余部分**时容易判断得多——真实页头、真实侧栏、真实数据、真实密度。单独的一次性路由处于真空之中：每个变体孤立地看都不错。只要存在一个合理的现有页面可以承载变体，就默认子形态 A。只有在原型确实没有就近宿主时才用子形态 B。

### 子形态 A——对现有页面的调整（首选）

路由已经存在。变体渲染在**同一路由**上，通过 `?variant=` URL 搜索参数控制。现有数据获取、参数和认证都保持不动——只有渲染部分切换。这是默认选择；除非有明确理由，否则选它。

如果原型对象还没有页面，但它*天然应该住进某个页面*（仪表盘的新区块、设置页的新卡片、现有流程的新步骤）——这仍属于子形态 A。把变体挂载进宿主页面。

### 子形态 B——新页面（最后手段）

只有当原型对象确实没有可以住进去的现有页面时才用——例如一个全新的顶层界面，或无法嵌入任何合理位置的流程。

创建一条**一次性路由**，遵循项目已有的路由约定——不要发明新的顶层结构。命名要明显是原型（例如路径或文件名包含 `prototype`）。沿用相同的 `?variant=` 模式。

在选定子形态 B 之前先自查：真的没有可以嵌入的现有页面吗？空路由会掩盖有内容的页面才能暴露的设计问题。

两种子形态的悬浮底栏完全相同。

## 流程

### 1. 说明问题并确定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪声——以 5 为上限。

在原型所在位置或文件顶部注释里，用一行写下计划：

> “设置页的三个变体，通过 `?variant=` 在现有 `/settings` 路由上切换。”

无论用户是否在场提出异议，这都有效。

### 2. 生成截然不同的变体

起草每个变体。让每个都满足：

- 页面的用途和它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，不论什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——布局不同、信息层级不同、主交互不同，而不只是颜色不同。三个略作微调的卡片网格不是 UI 原型，是壁纸。如果两份草稿太像，就带着明确的“不要用卡片网格”指引重做一份。

### 3. 把它们接起来

在路由上创建一个切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把现有数据获取全部放在切换器上方；每个变体只改变渲染子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的小型固定定位横条，包含三部分：

- **左箭头**——切换到上一个变体（循环回绕）。
- **变体标签**——显示当前变体键；如果变体导出了名字，也一并显示。例如 `B — Sidebar layout`。
- **右箭头**——切换到下一个（循环回绕）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架路由器——Next 用 `router.replace`，React Router 用 `navigate` 等），让变体可分享、刷新后仍保持。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比度胶囊、轻微阴影），让它明显不属于正在评估的设计。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等效检查做开关，这样误合入的原型不会把横条发布给用户。

把切换器放在单个共享组件中，让两种子形态都能复用。放在项目共享 UI 所在的位置。

### 5. 交接

把 URL（和 `?variant=` 键）展示出来。用户有空就会来回切换。有趣的反馈通常是**“我想要 B 的页头和 C 的侧栏”**——那才是他们真正想要的设计。

### 6. 捕获答案并清理

一旦某个变体胜出，先捕获答案——哪个变体以及为什么——再按 [SKILL](SKILL.md) 描述的方式捕获原型。把胜者折入真实代码，把其余放到一次性分支，而不是 main：

- **子形态 A**——把胜者折入现有页面；从 main 中删掉落选变体和切换器。
- **子形态 B**——把胜出变体提升为真实路由；从 main 中删掉一次性路由和切换器。

整套变体是一手来源，所以它要落到一次性分支，而不是垃圾桶——留在 main 里的变体组件和切换器会迅速腐烂，并迷惑下一位读者。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上有分歧。
- **变体之间共享过多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 就失去了意义。每个变体都应该可以自由丢弃布局。
- **把变体接到真实 mutation 上。** 只读原型没问题。如果变体需要 mutation，指向一个 stub——问题是“这应该长什么样”，不是“后端能不能用”。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（无测试、极简错误处理）。折入时要正确重写。
