# 逻辑原型

一个自包含的 HTML 文件——一个**可分享的演示**——任何人都能通过点击按钮来驱动状态模型。当问题关于**业务逻辑、状态转换或数据形状**时使用——这类东西纸面上看似合理，但只有推过真实用例后才会觉得不对劲。

因为它是一个无需安装的单文件，你可以把它交给非开发者——设计师、PM、领域专家——让他们亲手感受模型。所以它要说他们的语言，而不是代码的语言。

## 何时该用这种形态

- “我不确定这个状态机能否处理先 X 后 Y 的边界情况。”
- “这个数据模型真的能表示这种情况吗……”
- “我想在动手写 API 之前先感受一下它应该长什么样。”
- 任何有人想要**按按钮、看状态变化**的情况。

如果问题是“这应该长什么样”——分支错了。用 [UI.md](UI.md)。

## 流程

### 1. 说明问题

写代码之前，先写下你在为哪个状态模型和哪个问题做原型。一段话，放在演示顶部（放在可见简介里，不只是注释）。回答错问题的逻辑原型是纯粹浪费——把问题写明确，之后无论用户现在在看，还是稍后回来，都可以对照检查。

### 2. 把逻辑隔离成可移植模块

把真正的逻辑——回答问题的那部分——放进单个 `<script>` 块，写成一个小型纯模块，之后可以被提起并放入真实代码库。它周围的页面是一次性的；这个模块不是。

合适的形状取决于问题：

- **纯 reducer**——`(state, action) => state`。当动作是离散事件、状态是单个值时适用。
- **状态机**——显式状态和转换。当“此刻哪些动作合法”本身是问题的一部分时适用。
- **普通数据类型上的一小组纯函数**。当没有隐式当前状态——只有转换时适用。
- **具有清晰方法表面的类或模块**，当逻辑确实拥有持续的内部状态时适用。

选择最适合所问问题的形状，*而不是*最容易接到页面上的那个。保持纯净：不碰 DOM、不碰 `document`、不让按钮处理器伸进它里面。页面调用它；任何东西都不能反向流动。这正是让原型在自身生命周期之后仍有价值的原因：问题一旦得到回答，经过验证的 reducer / 状态机 / 函数集就能自行升入真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——无框架、无打包器、无服务器，全部内联，双击即开，经得起邮件转发。任何人都应该能打开即用。

为非开发者而写。每个标签都用**领域语言**，而不是代码——按钮和状态读起来像业务，而不是 reducer。用平实的话解释正在发生什么。

用清晰的自上而下层级来布局：

1. **标题和一句话说明**，说明这个演示能让你探索什么（第 1 步的问题）。
2. **当前状态**——完整相关状态，渲染为可读面板（带标签字段，不是原始 JSON 转储），每次点击后重新渲染，让变化可见。在能帮助非开发者跟上的地方，指出刚刚发生了什么变化。
3. **自由把玩按钮**——每个动作一个按钮，始终可用，任何人都能按任意顺序摆弄模型。每次点击派发对应动作并重渲染状态。
4. **引导式走查**——一组**场景**，每个场景一个页签。每个页签放一段简短的平实语言场景描述——它设置的情境和需要观察什么——下面放该场景的**按钮操作顺序**。每一步都是一个真实按钮：点击就执行该动作并进入下一步。开始一个走查会重置到已知初始状态，让场景每次都以相同方式运行。

选择能演示别扭情形的场景——快乐路径、棘手的边界情况、一次本应非法的尝试——那些纸面上难以推理的情况。

保持美观但克制：干净排版、充足留白、一种强调色。不要动画，不要花招——任何与状态和按钮抢注意力东西都不要。

### 4. 交接

把文件发给他们，或帮他们打开。他们有空就会点过走查和自由把玩；有趣的时刻是他们说“等等，这不应该可以”或“嗯，我原以为 X 会不一样”——这些是*想法*中的 bug，而这正是整个目的。如果他们想要新动作或新场景，就加上。原型会演化。

### 5. 捕获答案和原型

原型回答问题后，先捕获答案，再按 [SKILL](SKILL.md) 描述的方式捕获原型。logic 分支的映射：经过验证的 reducer / 状态机 / 函数集升入真实模块（决策被吸收）；HTML 外壳随同进入一次性分支，把原型作为一手来源保留——因为它是自包含单文件，在那里仍可轻松重新运行。

## 反模式

- **不要加测试。** 需要测试的原型不再是原型。
- **不要接真实数据库。** 除非问题明确关于持久化，否则用内存状态。
- **不要泛化。** 不要“如果我们以后想支持 X 怎么办”。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可提取。让页面成为纯模块之上的薄壳。
- **不要上框架、打包器或服务器。** 接收方双击即开的单文件；React 应用或开发服务器会毁掉“可分享”。
- **不要把 HTML 外壳送进生产。** 页面是为人工点击浏览而优化的。它后面的逻辑模块才是值得保留的部分。
