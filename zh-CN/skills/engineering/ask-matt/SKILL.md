# Ask Matt

你记不住每个技能，所以直接问。

**流程（flow）**是一条穿过这些技能的路径。大多数路径都沿一条**主流程（main flow）**行进，另有两个**匝道（on-ramp）**汇入其中。其余技能要么独立使用，要么是运行在底层的词汇层。

## 主流程：想法 → 交付

这是大多数工作会走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`**——通过访谈打磨想法。只要你在一个**工作目录中工作**，就从这里开始：它是有状态的，会把学到的内容保留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？用 `/grill-me`——见“独立技能”。两者运行的都是同一个 `/grilling` 原语；`grill-with-docs` 会留下书面记录，因此只要有仓库可以存放这些记录，它就是两者中更好的选择。）
2. **分支——你能在对话中解决所有问题吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、你必须亲眼看到的 UI），就绕道做一个原型，并在来去两个方向上都用 **`/handoff`** 搭桥（原型位于自己的目录中，这正是 `/handoff` 的用途——见“阶段边界”）：
   - **`/handoff`** 交接出去，然后针对该文件开一个新会话，
   - **`/prototype`** 用一次性代码回答这个问题，
   - **`/handoff`** 把你学到的东西交接回来，并在最初的想法线索中引用它。
3. **分支——这是一个跨多个会话的构建吗？**
   - **是** → **`/to-spec`**（把线索变成规格说明），然后 **`/to-tickets`** 把它拆成曳光弹 ticket，每个 ticket 都声明自己的**阻塞边（blocking edges）**。在本地跟踪器上，每个 ticket 对应 `.scratch/<feature>/issues/` 下的一个文件，按“先解决阻塞项”的方式手动推进；在真实跟踪器上，这些边会成为原生阻塞链接，因此任何阻塞项已完成的 ticket 都可以直接领取——为每个 ticket 启动 **`/implement`**，并在每个之间 **`/clear`** 清空上下文。每个 ticket 都是自包含的，所以上一个 ticket 的上下文用后即可丢弃。
   - **否** → 就在当前上下文窗口中直接 **`/implement`**。

   无论哪种方式，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个 issue——一次一个红-绿切片——最后在提交前运行 **`/code-review`**，对 diff 做一次双轴审查（Standards + Spec）。当你只想在没有完整规格的情况下测试先行地构建一个具体行为时，可以单独使用 **`/tdd`**；当你想对照固定点审查一个分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生

把步骤 1–3 保持在**一个不中断的上下文窗口**中——在 `/to-tickets` 之后才可 compact 或 clear——这样追问、规格和 ticket 都建立在同一套思考之上。每个 `/implement` 随后从 ticket 全新开始。

这一做法的限制是**[智能区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能清晰推理的窗口（最先进模型约 150k token）。如果会话在 `/to-tickets` 之前逼近这个限制，不要带着退化的状态硬撑——在最近的阶段边界执行 `/compact`，然后继续（见“阶段边界”）。

## 匝道

匝道是一种会产生工作、随后并入主流程的起始情形。

- **bug 和请求堆积** → **`/triage`**。它让 issue 经过各个分诊角色，产出 agent 就绪（agent-ready）的 issue，供 **`/implement`** 之后接手。

  分诊只用于**不是由你创建**的 issue——bug 报告、进来的功能请求、任何原始到达的内容。`/to-tickets` 产出的 ticket 已经是 agent 就绪的，所以**不要对它们分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于那些疑难杂症：一眼看不穿的 bug、时有时无的偶发失败、在两个已知良好状态之间悄悄混入的回退。在拥有一个**紧凑的反馈回路**——一条已经会因*这个* bug 变红的命令——之前，它拒绝凭空猜测；然后它会用回归测试修复。当事后复盘发现真正的问题是“没有好的接缝可以把 bug 锁死”时，它会转交 **`/improve-codebase-architecture`**。

- **一项庞大而迷雾重重的工作——绿地项目或单会话装不下的大型功能构建** → **`/wayfinder`**，这里是认知负担最重的流程。当从此处到目的地的路径尚不可见时，它会在 issue 跟踪器上绘制一张由**决策 ticket** 组成的**共享地图**，并一次解决一个——产出的是**决策，而不是交付物**——直到迷雾被驱散、路径清晰。**`/grill-with-docs`** 打磨的是你单会话能把握的想法；wayfinder 则用于你把握不了的想法——它更慢也更稠密，所以只留给这种情况，绝不要用在范围明确的功能上。

  地图清晰后，**它只交接，不构建**：在 **`/to-spec`** 处并入主流程，把地图上相互链接的决策折叠成可构建的计划，然后照常 `/to-tickets` 和 `/implement`。直接把地图丢进 `/implement` 会跳过这次折叠，丢掉相互关联的细节——只有当初估量证明这项努力确实很小时，才直接进入 `/implement`。

## 代码库健康

不是功能开发——是维护。

- **`/improve-codebase-architecture`**——有空就运行，让代码库保持适合 agent 在其中工作。它会找出**深化机会（deepening opportunities）**；选中其中一个会*生成一个想法*，你可以带着它进入 `/grill-with-docs` 的主流程。它是一次发现候选对象的普查；**`/codebase-design`**（见下）则是你设计所选对象的工作台。

## 底层词汇

两个模型调用的参考技能，运行在其他技能的*底层*——各自是其词汇的单一事实来源。当问题出在**用词**而非流程时，直接使用它们；也可以让上面的技能自行调用它们。

- **`/domain-modeling`**——打磨项目的*领域*语言：质疑模糊术语，理清被重载的词（一个 “account” 干了三件事），把难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 所驱动的主动纪律，让 `CONTEXT.md` 保持为一本干净的术语表。
- **`/codebase-design`**——设计模块*形状*所用的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：把大量行为放在干净接缝处的小接口后面。`/tdd` 和 `/improve-codebase-architecture` 都在使用这套词汇。

## 阶段边界

**阶段（phase）**是会话中的一块工作——追问、实现、QA。在两个阶段之间的**边界**处，你有五个选项；在整张地图中，从中做出选择是最模糊的决策：

- **Continue**——留在原地。不付出任何成本，也不丢失任何东西。
- **`/clear`**——清空窗口，用于这里的一切对接下来都无关紧要时。
- **`/handoff`**——写一份可移植的 markdown 文件。用途很窄：只用于**换新 harness**、**换新目录**、交给**同事**，或在**阶段中途**分叉一个支线任务。它换来的是可移植性。
- **Subagent**——把一个范围紧凑的任务发到它自己的窗口，然后拿回一份报告。
- **`/compact`**——压缩当前上下文，并用它启动一个新会话。它是**默认选择**，但位于决策树底部，而不是第一选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树——五个问题、每个分支背后的推理，以及为什么“一手来源”的成本让 **Continue** 成为首先应排除的选项。决策要在边界**处**做出；阶段中途，要么继续，要么把剩余工作拆给子 agent。

## 独立技能

完全脱离主流程。

- **`/grill-me`**——与 `/grill-with-docs` 同样毫不留情的访谈，但**无状态**：它不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时使用它——打磨计划、设计、文章等任何下面没有仓库的东西。如果你在工作目录中，请改用 `/grill-with-docs`：同样的访谈却会留下书面记录，因此严格来说它是更好的选择。
- **`/grilling`**——访谈原语本身：轮次、前沿、事实由 agent 负责而决策归你。`/grill-me` 和 `/grill-with-docs` 是两条具名的进入路径，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的访谈时，才直接使用它。
- **`/resolving-merge-conflicts`**——逐块处理进行中的 merge 或 rebase 冲突，按追溯到双方一手来源的**意图**来解决，而不是挑拣行；然后完成操作。它绝不运行 `--abort`。独立于所有流程之外：当你已经身处冲突之中时使用它。
- **`/prototype`**——一个小型一次性程序，回答一个设计问题：这个状态模型是否顺手，或者这个 UI 应该长什么样。“一次性”是对代码写法的一种约束，而不是承诺销毁它：答案会折入真实代码，原型本身则作为**一手来源**保留在 main 之外的 `prototype/<name>` 分支上，并由实现 issue 指向它。它是主流程第 2 步中的绕行路径，但只要设计问题难以在纸面上解决，随时可以使用。
- **`/research`**——把阅读这种跑腿工作委派给**后台 agent**：它对照**一手来源**调查问题，然后在仓库中留下一份带引用的 Markdown 文件。它阅读时你可以继续工作。它产出的文件是带入 `/grill-with-docs` 主流程的*素材*——研究为思考提供养料，而不是替代思考。
- **`/to-questionnaire`**——当卡住你的东西不在你脑子里或代码库里，而在**别人那里**时，它会写一份问卷给对方填写。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发出**这件事访谈你——发给谁、你需要拿回什么——然后把问题对准缺口。拿回来的内容可以成为 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`**——用于只有**人类**才能完成的步骤：配置基础设施、设置凭据或 CI 密钥、在陌生的第三方仪表盘中点击操作，或执行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、采集每个值，并写入 `.env` 和 GitHub secrets——这样这套流程就不再是每次都要向 agent 重新解释一遍的事情。它是模型调用的，所以 agent 一遇到只有你能通过的墙，就会伸手去用它。如果 agent 自己就能做，那就应该自己做；它只用于确实需要人在环中的场景。
- **`/wait-what`**——对没讲明白的消息的纠正手段。在任何其他技能内部、对话中途都可以使用；agent 会用你缺失的上下文、清晰直白的英语和 `CONTEXT.md` 词汇，把它刚说过的话重新讲一遍。它在事后才起作用；`/grill-with-docs` 是前置的解法，因为早早商定的共同语言才能让行话从一开始就无法出现。
- **`/teach`**——用多个会话学习一个概念，把当前目录作为有状态的工作区。
- **`/writing-for-agents`**——编写供 agent 使用的文档的参考：技能、AGENTS.md、被指针指向的文档。
